# SMILE 2.0 Studio — Accepted Design and Build Direction

**Decision date:** September 9, 2026, Asia/Manila.  
**Status:** Accepted product and architecture decisions; implementation status must be verified separately.  
**Repository:** `Sincioco/SMILE-2.0` — not the separate SMILE 1.0 repository.  
**Canonical repository destination:** `docs/architecture/2026-09-09 - SMILE 2.0 Studio.md`.

## 1. Authority, scope, and implementation status

Sin has accepted the recommendations consolidated here. This is the current design authority for Studio, its workspaces, scene/VFX/audio documents, and the relationship to declarative SMILE. Follow it instead of conflicting earlier conversations, downloaded handoffs, remembered plans, or superseded phase instructions.

This document replaces the earlier **battle-only editor**, **`.battle` native format**, and **separate required user-facing editor applications** as the intended destination. It also resolves the reusable asset extensions: use **`.smilevfx`** and **`.smileaudio`**, not a separate `.smilesoundfx` format initially.

Acceptance does not prove implementation. Do not label Studio hosting, generic saved-effect authoring, Water, scene playback/export, or declarative parity as implemented without current code and focused evidence. JSON examples and prose operation names in this document illustrate contracts; they are not a finalized schema or verified SMILE grammar.

This handoff authorizes recording the design, verified necessary hardening, documentation consolidation, and safe repository cleanup. **It does not authorize implementing the complete Studio product during cleanup.** Studio is the intended next work after the cleanup gate, with the first bounded implementation slice selected from actual remaining dependencies. Preserve unrelated user holds.

Existing language/runtime behavior remains authoritative for what works today; this record is authoritative for the planned product direction. A mismatch is a tracked implementation gap, not permission to claim the feature exists or change working code casually.

## 3. One application, several cohesive workspaces

```text
SMILE 2.0 Studio
├── Character Viewer
├── Character Editor
├── Animation Editor
├── Scene Editor
├── VFX
│   ├── Fire / Fire Lab
│   ├── Lightning / Lightning Lab
│   └── Water / Water Lab              [planned]
└── Audio
    ├── Music
    └── Sound Effects
```

Workspace selection chooses the activity. Document tabs identify the resources being inspected or edited. Fire Lab and Lightning Lab remain recognizable specialized workflows inside VFX; Music and Sound Effects are separate tabs inside Audio. The exact layout and supported first-version controls require implementation validation.

| Workspace | Owns | Does not own |
|---|---|---|
| Character Viewer | Read-oriented inspection of appearance, equipment, rig/clip information, diagnostics. | Accidental asset mutation or scene composition. |
| Character Editor | Supported character preparation, socket/equipment and pose corrections, explicit source-asset saves. | General modeling, sculpting, retopology, or an unrequested replacement for a digital-content-creation tool. |
| Animation Editor | Supported clip, keyframe, interpolation and pose-correction workflows. | A second runtime animation implementation or the timing of every scene object. |
| Scene Editor | Scene instances, transforms, authored cameras, composition, sequences, bindings and presentation cues. | Authoritative combat calculations or private copies of asset definitions. |
| VFX | Author/inspect reusable visual effects with specialized family controls and common preview/save behavior. | One universal simulation forced onto Fire, Lightning, and Water. |
| Audio / Music | Prepare/audition music assets and supported cue, loop, fade, transition and gain settings. | A full digital audio workstation as an initial requirement. |
| Audio / Sound Effects | Prepare/audition effects and supported one-shot/looping, gain, fade and variation settings. | A separate audio engine or hidden rewriting of original media. |

A future Code workspace is optional. Neither a new IDE nor arbitrary BASIC-to-visual round-tripping is required to build Studio.

## 4. Construction strategy and module boundaries

Build one **thin Studio application host**, in the same repository, around existing shared capabilities and incrementally hosted tool modules. Preserve the existing Viewer and labs while migrating actual workflows. Do not clone their implementations into permanently diverging copies, embed multiple independent application windows as a substitute for modular hosting, or rewrite their foundations from scratch.

Temporary standalone launchers may remain as thin development/regression harnesses that call the same implementation. Separate required user-facing applications are not the final destination.

The host owns window/application coordination, built-in workspace registration, focused input/command routing, document-open/close coordination, and session shutdown. It must not implement wrist correction, fire simulation, scene serialization, audio mixing, or declarative compilation.

Related state, behavior, validation, and lifecycle belong together behind narrow contracts. Reuse shared modules directly when suitable. Extract additional behavior only when a concrete hosted workflow needs it; switch the original caller to the shared implementation and remove duplication before declaring extraction complete.

Do not introduce a giant `StudioState`, renamed Viewer controller, global mutable context, or `IsSceneEditor` branches throughout the Viewer. New records, wrapper files, line-count reductions, or green tests alone do not prove responsibility extraction. Flag architectural drift before adding more responsibilities.

Start with explicit built-in modules, not a plugin platform, dynamic discovery framework, separate process architecture, new package manager, or npm-based sharing mechanism. Reuse current project/library mechanisms and the existing compiler/runtime. A small required standalone helper can use dependency-free JavaScript; do not change the repository's established implementation stack as a cleanup exercise.

Follow repository guardrails. Where an area has none, use review triggers around **300 lines for a new orchestration entry point** and **600 lines for a new feature module**. Review ownership at those thresholds; do not split mechanically. Respect documented exceptions in established code and do not reopen the completed Viewer refactor solely because a file exceeds a proposed new-code trigger.

Native Windows is priority 1, Web priority 2. Use Chrome as the primary browser unless a current browser-specific problem justifies another engine. Preserve first-class 2D rendering for text, images, HUDs and overlays alongside 3D. Shared source does not mean shared mutable session state.

## 5. Document ownership, undo, and local state

Use one authoritative editing session per open resource; several workspaces may operate on it through supported document operations. Scope dirty state, validation, save, and undo/redo to the document, not merely to the currently selected workspace.

Distinguish **Edit Source Asset**, **Override in This Scene**, and **Save As New Asset**. A sword-attachment correction can belong to a character asset; moving Arin within one cinematic belongs to the scene. Scene-specific changes must not rewrite canonical character packages. Export must not overwrite handwritten `.smile` unnoticed.

A failed save leaves the document dirty and preserves the previous valid file. Workspace switching must not silently save, discard, or duplicate the editable resource. Cross-document operations require explicit ownership; do not invent a universal transaction system before one is needed.

Initially, propagate explicitly saved/applied source-asset changes through a controlled dependent-preview refresh/restart. Do not invisibly propagate unsaved edits or mutate live instance state halfway through a frame. Preserve document identity so stale load results cannot attach to a closed or replaced document when asynchronous loading is introduced.

For the first host, prefer one active interactive viewport. Inactive workspaces retain authoring state while suspending unnecessary preview/input/audio work. A preview may still play music and several sound effects concurrently. Independent instances own their transforms, animation positions, random state, effect state, cameras and resource leases. Closing one preview must not invalidate another owner's resources. One host coordinates frame timing; workspaces must not create competing top-level update loops.

Local application/session state normally remains untracked. Reuse existing preference ownership where suitable; do not create competing window-placement stores. Moving an inspection camera, changing panel sizes, selecting an object, seeking the playhead, or reducing audition volume is not an authored scene change.

## 6. Persistence boundaries

| File/store | Authoritative contents | Excluded contents |
|---|---|---|
| `.smilestudio` | Small, portable workspace identity, project references, and genuinely shared authoring organization. | Duplicate build declarations, runtime behavior, media payloads, personal open-tab/panel state. |
| Existing `.smileproj` / `.smilelibproj` | Established project, source, library, dependency, asset and publication declarations. | A second competing definition copied into Studio. |
| `.smilescene` | Scene content, asset references, instances, attachment bindings, authored cameras, sequences, cues, supported overrides. | Studio session settings, inspection cameras, playheads, preview caches. |
| `.smilevfx` | Reusable visual-effect recipe, supported parameters, required inputs/capabilities and dependencies. | Hard-coded Arin/sword/scene identity, live particles, lab UI state. |
| `.smileaudio` | Reusable music or sound-effect cue recipe and declared source-media dependencies. | Embedded waveforms, audition UI state, a second audio engine. |
| Canonical character/equipment/animation packages | Existing asset source, rig, animation, socket/region metadata and accepted corrections. | Disposable preview copies masquerading as source. |
| Local preferences/session/cache/recovery | Personal inspection state, UI layout, temporary previews, thumbnails, waveform caches, recoverable unsaved work. | Runtime-required asset lookup data available only in Studio. |

A possible ignored per-workspace session filename is `SinStarI.smilestudio.user.json`; exact placement is not finalized. Recovery files need explicit ownership and safe cleanup, not blanket deletion merely because they are local.

A minimal `.smilestudio` shape could be:

```json
{
  "format": "smile-studio",
  "formatVersion": 1,
  "id": "sin-star-i-workspace",
  "name": "Sin Star I",
  "projects": [
    { "id": "sin-star-i", "path": "SinStarI.smileproj" }
  ]
}
```

This example does not fix every schema field or make version 1 an implemented loader contract. Start small; add shared collections only for real workflows.

Studio should open a standalone scene without requiring a workspace manifest. Runtime assets, scenes, and exported/source-authored programs must resolve their declared dependencies without `.smilestudio`, open Studio tabs, or editor caches.

## 7. Human-readable and safe document contracts

Use strict human-readable UTF-8 JSON for the four new document families. Keep one authoritative schema/semantic contract for each supported format. Scene, VFX and audio definitions carry explicit format and semantics versions; the workspace manifest needs explicit format versioning, with semantic versioning only if genuinely necessary for its non-runtime role.

Preserve stable IDs, portable external/logical references, deterministic formatting and stable property ordering. Preserve semantically ordered arrays and execution order. Do not insert incidental save timestamps, machine-specific paths, caches, binary payloads, generated IDs on every save, or runtime playback state. Notes belong in defined text fields rather than a custom JSON-comment dialect.

Schema validation is not semantic validation. Check referenced IDs, units, coordinate spaces, defaults, ranges, binding compatibility, sequence order, cycles where prohibited, supported capabilities, dependency availability and resource requirements. Validate declared paths within authorized roots. Treat definitions as data, not arbitrary executable plugins.

Use transactional safe writes and the existing persistence patterns. Reject malformed or unsupported runtime-affecting content rather than silently stripping it. Do not overwrite a newer unsupported document with a reduced older representation. Preserve original bytes until a supported migration succeeds. Make unsupported versions and fields actionable diagnostics. Do not implement a universal migration framework in advance of actual format evolution.

Stable IDs survive normal edits and supported moves; Save As New Asset creates a distinct identity. Report duplicate-ID conflicts. A rebuildable index must not choose a conflicting asset according to discovery order.

## 8. General scenes, not battle-only documents

Scene Editor authors presentation for battles, non-battle cutscenes, introductions, conversations, character showcases, boss transformations, cinematics, and eventually interactive scenes. These are intended capabilities, not a claim that dialogue, branching or every cinematic control exists today.

The general scene contract covers supported actors/objects, assets, transforms, environments/stages, authored cameras, animation, lighting/material/VFX/audio settings, sequences, cues and external bindings. It is not the editor's UI state and not the declarative frontend's syntax tree.

Battle is an optional consumer/integration. The shared presentation runtime emits cues; Sin Star I combat owns authoritative damage, health, turn order and target rules. A sword-impact cue may synchronize presentation without granting the editor authority to calculate damage. No enemy, fixed party roster, boss, attack sequence or turn system is required to open or run a scene.

Preserve the reflective-floor contract: the background bitmap remains screen-fixed while the arena rotates relative to it; eligible live characters/equipment and supported VFX reflect through the shared renderer. Do not bake a background reflection into a rotating floor texture. Keep supported floor/VFX reflection toggles, scene visibility and matte fallback behavior. Reflection capture replays accepted render state; it must not update actors, consume emitter admission, or advance simulation again. Authored reflection choices belong to the scene; an explicitly temporary inspection override remains local.

Generalization must be behavioral, not a cosmetic `BattleScene` to `Scene` rename retaining fixed battle assumptions. Conversely, keep genuinely combat-specific integrations separate rather than erasing them.

## 9. Reusable VFX: definition, instance, binding

`.smilevfx` is a SMILE runtime asset that Studio edits, not a Studio-only preset. Fire, Lightning and future Water share discovery, document lifecycle and preview coordination where appropriate, while retaining their own supported parameters and execution algorithms.

| Responsibility | Owner |
|---|---|
| Appearance, emission/timing recipe, dependencies and required placement inputs | Reusable `.smilevfx` definition. |
| Which character/equipment/object uses it, activation timing and supported instance overrides | `.smilescene` instance or equivalent declarative scene code. |
| Bone/socket identity and blade endpoints/contours/surface regions | Canonical character/equipment metadata. |
| Live particles, clocks, random state, admission, disposal and renderer leases | Runtime effect instance and established shared services. |
| Demonstration blade, selected panel, audition/preview camera | VFX workspace preview/session. |

A reusable blade effect can require a point, line, contour or supported surface input. Do not make it depend on Arin, a particular lab station, an open tab, or the Viewer profile list. Do not build a complete mesh-surface emitter if an existing line/contour operation satisfies the first use case.

Equipment-bound effects follow the final animated, grounded, calibrated weapon transform. An attachment point answers where the emitter is; blade geometry answers where it emits. Make simulation-space policy explicit: the emitter can follow the sword while already-emitted embers remain in world space. Missing sockets or incompatible geometry must diagnose the binding, not silently attach to the actor origin.

Share immutable definitions and resources where supported; keep mutable instance state independent. Preserve whole-scene budgets, atomic admission/fallback, hide/freeze/reset/discontinuity cleanup and retry semantics. Do not reserve all effect capacity for one character or double admission for reflections.

Water belongs under VFX when implemented. It is not implemented by naming a new definition type, and it is not a requirement to create a full fluid simulator before Studio can host existing effects.

## 10. Shared asset catalog and the flaming-sword workflow

The project asset catalog is a small, rebuildable index over canonical declared assets. It is not another editable copy of their settings and is not a Studio-only runtime path resolver. Project declarations and established asset/publication services own roots and deployment dependencies.

Start with discovery when a project opens, direct catalog invalidation/notification after a successful Studio save, and explicit Refresh Assets. File watching may complement these operations; it is not the sole correctness mechanism. Discovery reads metadata without automatically instantiating emitters, loading every media payload, or playing audio.

The concrete accepted workflow is:

1. In VFX → Fire, author **Sword Ember** and save `sword-ember.smilevfx` in a declared project asset location. Save its supported recipe and input requirements, not the preview character.
2. After successful persistence, the shared catalog exposes its stable identity and type/category. A failed save does not publish an invalid new asset.
3. Scene Editor's Project Assets browser lists Sword Ember regardless of whether Fire Lab is open. No direct Fire Lab-to-Scene Editor panel call is required.
4. Select Arin's sword, choose Add Effect or drag the definition onto the equipment. Create an independent scene instance, bind it to actual weapon metadata/blade geometry, and set supported overrides/timing.
5. Save `.smilescene` with that reference and binding. Do not copy the complete fire definition into the scene by default.
6. Close Fire Lab, reopen the scene, and resolve/instantiate the effect through the shared loader. Its placement follows the calibrated animated sword.
7. Load the same definition through declarative SMILE without Studio. Directly express the supported definition parameters in code when that authoring mode is used.

Editing the source effect, overriding this instance, and duplicating the definition have explicit UI actions and save ownership. Refresh dependent previews at a safe point; do not retain hidden obsolete instances or leak leases after reload.

## 11. Audio definitions and cue ownership

Introduce **one `.smileaudio` format** initially. Both Music and Sound Effects use it; a category selects authoring organization and controls, while explicit playback settings determine runtime behavior. Do not create a separate `.smilesoundfx` parser/schema/loader merely because Sound Effects has a separate tab.

Examples of reusable assets are `battle-theme.smileaudio`, `sword-ignite.smileaudio` and `fire-crackle.smileaudio`. They reference source audio and supported cue/gain/loop/range/fade/transition/variation settings. The file is a recipe, not embedded waveform data. Preserve original media for non-destructive edits.

Only expose processing the shared runtime can reproduce. Unsupported equalization, reverb or other processing needs an explicit runtime capability or a clearly identified rendered-media workflow; accepting a JSON field does not implement audio processing.

Use common loading, playback, mixing, resource ownership and focus behavior. Keep Studio audition volume separate from the authored mix. One scene can play music and overlapping sound effects; inactive workspace previews must not continue accidental hidden audio. Stop/reset/close releases the preview's own channels and scheduled cues, not unrelated application audio or the operating system's master volume.

VFX may explicitly own an associated audio cue, or the scene may schedule it. Never have both independently trigger the same thunder or ignition sound unknowingly. Cue timing belongs to shared definitions/runtime sequencing, not a tab-local timer. Preserve applicable reduced-flash/comfort controls and scene-level policy; do not bypass them through a new asset file.

## 12. Independent declarative authoring and one shared runtime

Visual and declarative authoring are **independently developable implementations with coordinated semantics**. Either may advance first. They target shared validated scene/sequence and asset definitions and the existing SMILE compiler/runtime; no second engine, duplicated playback algorithm, or separate editor-only compiler.

```text
Scene Editor → .smilescene / scene definition ───┐
                                                ├→ Shared scene/sequence runtime
Declarative .smile → shared compiler → definition┘
                                      ↑
          Shared .smilevfx / .smileaudio loaders
```

Editor preview must work without declarative export. Declarative execution must work without editor components. Lowering and source export operate on scene semantics, not UI controls or private editor objects. General camera/effect/audio operations remain general; battle bindings are optional.

Evolve readable object-first/action-after BASIC syntax where needed. Do not freeze outdated illustrative grammar, invent many aliases, or silently repurpose core syntax. Integrate language changes through the shared language/semantic implementation and update diagnostics, tests, examples and tooling together. Preserve the practical shared-core compatibility direction in section 2.

Loading a reusable definition and creating/starting an instance are separate operations. Exact syntax, units and defaults must be specified and verified against the real compiler when implemented. A JSON loader alone is not proof that programmers can author every supported parameter declaratively.

Dynamic loading supports new data using existing supported capabilities. A new algorithm still requires compatible runtime support. Publication must include the declared definition and transitive textures/media/other allowed dependencies. Dynamically selected paths require an explicit inclusion/content-source contract; a runtime string is not proof that a file was packaged. Handle loading errors and capacity exhaustion without partly constructed live instances.

## 13. Faithful exports and authoring authority

Export **real readable `.smile` source**. It must run with a compatible compiler/runtime and its declared media/assets/game bindings, without Studio or the original `.smilescene`. Include required setup/entry behavior for a standalone preview, or expose an explicit reusable game-binding contract for integration.

A generated program that merely loads the original `.smilescene`, embeds its JSON in a string, or relies on hidden generated editor state does not satisfy scene export. Preserve asset resolution when exporting into another location through explicit roots or correctly rewritten references.

Two explicit modes are accepted:

| Export mode | Meaning |
|---|---|
| Reference-preserving | Generate readable scene/instance/binding/sequencing code referencing declared reusable `.smilevfx` and `.smileaudio` definitions. Those dependencies remain required. |
| Expanded declarative | Express statically known effect/audio definitions using supported declarative language constructs; underlying media can remain external. |

Never switch export modes silently. An external definition that is genuinely selected at runtime cannot necessarily be expanded ahead of time; retain the declared dependency in the reference mode or explain why expanded export is unavailable.

Reference-mode loading can be a valid reuse path without proving full definition-authoring parity. Record any parameters that still lack direct declarative expression. Expanded mode must diagnose them instead of inserting disguised JSON. Unsupported scene behavior blocks faithful export of scenes that use it, not every unrelated scene. Do not approximate away settings or drop unsupported cues to make an export succeed.

`.smilescene` is authoritative for visual authors; handwritten `.smile` is authoritative for programmers. Generated source is derivative until deliberately taken over. Export destinations and overwrite behavior must protect handwritten changes; no false bidirectional synchronization claim.

## 14. One-to-one parity and evidence

The goal is one-to-one **runtime scene feature, parameter and behavior parity** in both directions, not identical UI features and not arbitrary BASIC source-code round-tripping. A parser keyword or similar initial screenshot is insufficient.

Maintain one machine-readable capability register and a generated Markdown view named `scene-feature-parity.md`. Reuse an appropriate existing register before adding one. Do not maintain independently edited competing tables. Establish the minimal register when the first shared scene/asset capability slice is implemented; document its intended owner during this cleanup without fabricating current green statuses.

For each capability record: stable ID; runtime/target support; scene or asset persistence; editor authoring; declarative syntax/lowering; reference and expanded export support where relevant; versions; defaults/units/limits; focused evidence; and every missing/partial/unverified counterpart with an owner and target milestone. Owners identify cohesive subsystems, not extra parallel agents.

New features may ship first on one authoring path when their counterpart is explicitly recorded. Already-established parity must not regress silently. A milestone declared fully equivalent must close its in-scope gaps with evidence. A broad row such as Reflections or Camera is not enough when strengths, easing, spaces, ordering, or interruption policies differ.

Required focused proof for implemented capabilities includes:

- Native document load/save produces equivalent normalized semantics without losing meaningful order or authoring data.
- Exported source compiles through the real shared compiler and yields equivalent normalized scene/asset meaning; normalization must not erase actual differences.
- Expected state/event traces and representative visual outcomes agree under controlled inputs/time/seeds. Compare known expected results, not just two paths that could share the same bug.
- Standalone export executes without Studio and without the original `.smilescene`; declared dependencies remain explicit.
- Reflection tests preserve fixed background versus rotating floor, moving characters, toggles/fallback and once-per-frame simulation.
- The flaming-sword case validates metadata-driven calibrated placement, independent repeated instances, safe hide/reset/dispose/reload and runtime-only loading.
- Audio proves supported overlap, timing, preview isolation and no duplicate cue emission.
- A missing capability produces a specific diagnostic; scenes that do not use it remain exportable.

Use proportional tests within existing runners. Do not create an exhaustive matrix, repeated browser passes, or a giant acceptance framework without a real defect requiring it.

## 16. Lean documentation and maintenance policy

**The active repository is a current engineering reference, not a museum of completed repairs.** Sin explicitly does not want permanent incident dossiers, H-number closure catalogs, old evidence bundles, refactor diaries, or a replacement summary for every completed hardening task.

Keep current contracts, ownership, commands, active limitations, design decisions, and the tests needed to protect supported behavior. Once a completed report contains no unique current information, delete it from the active tree. A current rule learned during a repair belongs in the relevant current owner documentation, written in present tense without an obligatory retelling of the incident.

For example, retain **“Reflection capture replays frozen submissions and never advances simulation”** in the rendering contract and its focused test. Do not require a permanent dossier saying which historic issue discovered that rule, every attempted fix, screenshots of the old failure, and a closure certificate.

A retired report does not need a tombstone or a new closed-bug ledger. Previously committed history remains available through Git when a real investigation needs it; normal task startup must not require rereading completed findings. Detailed task inventories, deletion maps and validation transcripts can be temporary/local or delivery artifacts rather than new tracked backlog files.

`AGENTS.md` routes tasks to this accepted design and current owner documentation. Remove obsolete mandatory routes to retired closure files and update affected consumers in the same change. When a script exists only to preserve or verify an obsolete evidence bundle, it too is a retirement candidate. If it also enforces a current semantic or structural invariant, preserve that behavior in an appropriate current check rather than retaining historical metadata by default.

Do not remove actual unresolved work merely because its old phase label is obsolete. Consolidate it into one appropriate current status owner with accurate scope, a responsible owner and next action. A current documented size exception can remain with its present rationale; the entire refactor chronology need not remain with it. Keep license/provenance, current asset checksums and version-specific operating/repair instructions where they remain necessary: those are current asset contracts, not old incident paperwork.

Future audits must assess the current source, reachable behavior, applicable contracts and focused tests. Do not report a closed historic finding as open just because an old plan mentioned it. A new finding needs current supporting evidence or a clearly identified current code-path/counterexample analysis. An unverified concern must be labeled as such. Passing tests and old closure certificates are neither blanket proof of correctness nor reasons to suppress a demonstrated new defect.

A correct fix should not be reported as outstanding while the fix and applicable contract remain valid. Later changes can reintroduce the behavior; audits can miss defects or raise mistaken concerns. **No claim of permanent immunity from regression is made.** Historical documentation is not the primary protection: correct implementation, current contracts and proportional regression tests are.

A fixed bug alone does not make its regression check obsolete. Retire tests/programs whose supported behavior disappeared, temporary investigations with no ongoing value, and proven redundant cases/harnesses. Where coverage is still needed, preserve the assertions in a simpler retained test. Do not delete failing tests to make the repository look green, and do not demand permanent retention of every historic reproducer or stress experiment.

Git history is the normal archive for previously committed obsolete tracked files. Do not rewrite history or create a tracked Archive folder of stale instructions. Untracked/ignored source assets, licensed originals, calibration, recovery data and user work are not recoverable from Git merely because their containing project is tracked.

The accompanying numbered instructions govern this cleanup. They are short-lived execution material and must not become another permanent collection of obsolete handoffs after completion. Update focused current documents rather than creating a new dated report for every subsequent task.
