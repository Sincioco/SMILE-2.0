# Phase 9 RPG battle-system gap matrix

This matrix was completed before Phase 9 production code changed. It compares the required battle behaviours with the reviewed Phase 7, 7.1, 8, and 8.1 packages and public gallery applications. Private PS1 and PS2 projects are excluded from this review because Sin paused all work on those projects until further notice.

| Required capability | Existing authority or reusable seam | Classification and decision |
|---|---|---|
| RPG-state identity and generation-safe handles | `Smile.RPG.Core` | Existing authority/reuse. Battle state uses the same bounded state slots and rejects stale handles; no second RPG-state model is added. |
| Persistent character identity, HP, MP, base statistics, levels, and EXP | `Smile.RPG.Characters` | Existing authority/reuse. Battle participants reference existing character IDs, and committed battle results use the existing mutation APIs. |
| Party order, active membership, and Gold | `Smile.RPG.Party` | Existing authority/reuse. The first four party positions form the active battle party; no second party or currency model is added. |
| Items, inventory quantities, equipment, and learned abilities | `Smile.RPG.Inventory`, `Smile.RPG.Equipment`, and `Smile.RPG.Abilities` | Existing authority/reuse. Item consumption and MP payment are transactional battle actions. Public terminology remains Ability and MP. |
| Pending encounters and deterministic encounter seeds | `Smile.RPG.Encounters` | Existing authority/reuse. Applications translate a pending encounter into a registered battle formation and explicit seed. |
| Exact return to top-down, overworld, and first-person exploration | `Smile.RPG.World` return locations and stable scene/spawn IDs | Existing authority/reuse. The application records the existing return location, presents battle, and restores the exact prior exploration state after resolution. |
| One active battle per RPG state | None | Missing generic API/new module. `Smile.RPG.BattleCore` owns the bounded lifecycle, generation-safe battle handle, and active-session guard. |
| Enemy and formation definitions | None | Missing generic API/new module. `BattleCore` owns at least 64 enemy definitions, 32 formations, four enemy groups, and eight simultaneous enemies. Stable integer IDs are caller-assigned. |
| Battle participants and transient battle statistics | Persistent character data exists, but no transient battle instance exists | Missing generic API/new module. `BattleCore` creates bounded character/enemy instances without duplicating persistent character, party, or inventory authority. |
| Commands, target legality, deterministic retargeting, round order, and one-action-at-a-time resolution | None | Missing generic API/new module. `BattleCore` implements Attack, Ability, Item, Defend, and Run with deterministic scheduling and explicit target policies. |
| Damage, healing, MP restore, status application/removal, revive, and composite effects | Ability definitions exist but do not resolve battle effects | Missing generic API/new module. `Smile.RPG.BattleEffects` owns at least 128 effect definitions and 32 status definitions; `BattleCore` applies them atomically. |
| Poison, action denial, statistic modifiers, durations, and end-of-battle cleanup | None | Missing generic API/new module. Status timing is deterministic, bounded, and transient. Persistent ailments are explicitly deferred. |
| Standing Fight orders, Order editing, repeat policies, after-round interrupt, Run, and deterministic enemy AI | None | Missing generic API/new module. `Smile.RPG.BattleStrategy` owns at least 64 bounded strategy/AI definitions and submits validated orders to `BattleCore`. |
| Victory, defeat, escape, EXP, and Gold | Character EXP and party Gold APIs exist, but battle settlement does not | Missing generic API/new module. `BattleCore` preflights and commits rewards once, atomically, to every eligible active character and the existing party wallet. |
| Renderer-neutral battle events | None | Missing generic API/new module. `BattleCore` exposes a bounded inspectable event stream for lifecycle, actions, effects, messages, outcomes, and rewards. |
| Logical actor slots and presentation cues | None | Missing generic API/new module. `Smile.RPG.BattleView` maps events into bounded X/Y/Z, facing, layer, anchor, pose, movement, effect, number, message, shake, sound, wait, hide, and reward cues. It performs no drawing or audio. |
| Future 3D presentation seam | No battle seam; existing renderer APIs are application-facing | Missing generic API/new module only at the data boundary. Logical slots and cues remain renderer-neutral; an actual 3D renderer is explicitly deferred. |
| Determinism and headless bounded execution | Existing RPG modules use bounded integer state | Missing generic battle implementation. Battle resolution accepts an explicit seed, uses no wall clock or implicit randomness, and exposes update-step progression suitable for native/Web parity tests. |
| Save/load boundary while battle is active | `Smile.RPG.SaveGames` serializes SRPG 2 but has no battle guard | Missing generic integration. `SaveGames` will reject encode, decode, save, and load while `BattleCore` reports an active battle. Battle sessions are never serialized; SRPG 2 remains unchanged. |
| Native/Web state-machine parity and injected rollback failures | Existing Phase 7/8 state tests and disposable-source fault scripts | Missing Phase 9 validation. Add `Phase9BattleStateTests` plus private disposable-source fault injection after MP payment, item removal, first multi-target application, status composite mutation, first character reward, and Gold reward. No test hook enters public APIs. |
| Three public battle presentations and exploration integration | `Smile.Game`, `Smile.UI`, `RpgWorldGallery`, and `RpgDungeonGallery` provide application patterns | Application presentation. Add `RpgBattleGallery` with original redistributable high-resolution art/audio and overworld, top-down, and first-person entry/return demonstrations. |
| Drawing, animation, audio, input, menus, camera, battlefield layout, and art | `Smile.Game`, `Smile.UI`, and the application | Application presentation. The four battle modules contain no `Game Window`, image/audio load, drawing, or UI calls. Windows DirectX is validated first, followed by GDI and Web at DPR 2. |
| PS1 and PS2 private capability demos | Private projects outside Git | Initially user-deferred while the public implementation proceeded. Sin later resumed this work; the private projects were then extended, built, smoke-tested, and included in the copyright audit without bringing commercial material into Git. |
| Active-battle persistence and a new SRPG format | SRPG 2 persists only durable RPG state | Explicitly deferred/out of scope. Battle state is transient, and no SRPG 3 writer is introduced. |
| Complex loot tables, automatic level curves, persistent ailments, Phase 10/11 work, and a general 3D engine | None required by Phase 9 | Explicitly deferred/out of scope. Phase 9 implements only the bounded reusable battle authority and its required public proofs. |

## Result

Phase 9 proves a genuine reusable-library gap. The package needs four ordinary modules: `Smile.RPG.BattleCore`, `Smile.RPG.BattleStrategy`, `Smile.RPG.BattleEffects`, and `Smile.RPG.BattleView`. They compose the existing character, party, inventory, ability, encounter, world, and persistence authorities rather than replacing them.

The battle session, effects, statuses, strategy orders, AI decisions, events, slots, and cues are bounded transient state. Applications own every visual and audible choice. SRPG continues to write version 2 and read versions 1 and 2; `.smilelib` remains format 5; SMILE-MAP remains version 1. The intended package change is `Smile.RPG` 1.2.0, with unrelated packages unchanged unless their shipped implementation must change.

Private PS1/PS2 work was paused by explicit user instruction when this pre-production matrix was created. Sin later lifted that pause, so the private battle demonstrations and their repository-safety audit were completed before Phase 9 closure.
