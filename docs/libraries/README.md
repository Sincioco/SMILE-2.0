# SMILE 2.0 libraries

A `.smilelibproj` declares `ProjectKind` `Library`, `LibraryName`, semantic `Version`, optional `OutputName`, `SmileSource` items, and optional `SmileProjectReference` or `SmileLibraryReference` items. It has no startup file and builds to `bin\Debug` or `bin\Release` as a `.smilelib`.

The package is a deterministic ZIP with a fixed timestamp, ordinal entry order, LF UTF-8 source, no compression, `manifest.json`, `api/public-symbols.json`, and `src/` entries. Both metadata documents use format version 6. The manifest records the library name/version and canonical `LibraryName@major.minor.patch` provider, exported module names, dependency identities, exact `src/<project Include>` source IDs, and SHA-256 source hashes. Public API metadata repeats that canonical library identity and preserves one ordered module-member namespace across constants, variables, arrays, routines, enums, Types, and Classes. Type references are structured `primitive`, `enum`, `type`, or `class` objects; nominal references retain exact module, runtime identity, and provider. Declarations use `{source,line,column,length}` locations tied to archive source IDs rather than checkout or extraction paths. Routine metadata preserves parameter names, declaration order, `ByVal`/`ByRef` mode, optional/default values, return type, visibility, and `requiresGameWindow`. Enum entries preserve ordered member names and numeric values. Type and Class entries contain structural fields plus a nested member container for constructors, methods, functions, and properties/accessors as those language symbols apply. Private module members and private nominal types are absent, and public signatures cannot expose private types. Formats 1 through 5 are rejected through `SML3206` as no longer supported, with an instruction to rebuild for format 6.

Loading rejects duplicate, undeclared, executable, absolute, traversal, malformed, or hash-mismatched payloads before content enters analysis. The loader retains each declared archive source ID alongside its extracted physical document. Authoritative validation reparses those sources with exact dependency boundaries, regenerates format-6 public API bytes, and requires byte equality with `api/public-symbols.json`. Extracted source is cached under `obj\Smile\Libraries\<name>\<version>\<package-hash>`; changing package bytes selects a new cache directory. Package fingerprints compare format, identity, modules, normalized source hashes, dependencies, and the public API hash without relying on timestamps.

Application and library projects may reference another `.smilelibproj` or a built `.smilelib`. One resolver in `Smile.Language` treats project sources and packages as exact providers, builds a deterministic dependency graph, validates dependent packages with all explicitly supplied dependencies present, and rejects implicit restore or provider fallback. The shared dependency context allows same-provider imports and direct project/package edges only. An application cannot import a transitive provider, a library project cannot use an ambient sibling provider, and package-owned sources can use only exact dependencies declared by that package manifest. A loose root and its `--source` files may use every package supplied directly with repeated `--library`, while package sources retain their manifest boundaries. `Import` completion uses the same access decision.

Project compilations and loose `smilec --library` builds use this same resolver. Project references build dependency-first, reject cycles, and retain real source paths for native project-reference debugging. Package dependencies must be supplied explicitly at matching `major.minor.patch` versions. An existing project-reference output is reused only when its package format, library name/version, owned modules, normalized source entry paths and SHA-256 hashes, exact direct dependency identities, and derived public API metadata match the current project; timestamps alone are not authoritative.

Expected project and library failures use these shared diagnostics in the compiler and editor:

| Code | Meaning |
| --- | --- |
| `SML3200` | A referenced project, package, or required provider is missing. |
| `SML3201` | A normalized package path, library identity, or physical source has conflicting providers. |
| `SML3202` | The supplied provider version does not exactly match the dependency version. |
| `SML3203` | One manifest declares the same dependency more than once. |
| `SML3204` | A library declares itself as a dependency. |
| `SML3205` | A package dependency or project-reference graph contains a cycle; the message includes the cycle path. |
| `SML3206` | Project or package structure is malformed or unsupported. |
| `SML3207` | Package-owned sources, module metadata, or public API metadata fail authoritative dependency-aware validation. |
| `SML3208` | An import resolves to a provider that is not the importing source's own provider or a declared direct reference. |
| `SML3209` | Project or package data cannot be read. |
| `SML3299` | Visual Studio recovered from an unexpected analysis failure and logged the exception. |

Dependency-resolution messages identify the dependent library and version, required provider and exact version, actual provider when present, and relevant physical paths. `SML3208` is attached to the physical `Import` module-name span. Expected project and package failures use `<path>(1,1): error SML32xx: <message>` when no source span exists and return compiler exit code 1; exit code 2 is reserved for usage or infrastructure failures. Package API validation compares only modules owned by that package, so dependency modules never leak into its public metadata.

In Visual Studio 2026, create **SMILE 2.0 Library** from File > New > Project. Every SMILE project shows References; **Add SMILE 2.0 Library Reference...** and **Remove Reference** refresh Solution Explorer and IntelliSense immediately. Focused watchers use tolerant graph discovery and retain last-known participating paths, newly discovered paths, missing reference paths, and existing parent directories. Direct or transitive project/package restoration and atomic package replacement therefore reanalyze without a solution reload. Broken references keep local editing and the stable shared diagnostic alive. Visual Studio preflight and compiler diagnostics use the same path/line/code/message form in Output and Error List and clear stale build entries. Before a build or F5, Visual Studio saves every open physical source reachable through project references; extracted package-cache sources are never saved. Library F5 reports that the project is non-runnable. `Import` offers only same-provider and directly accessible modules. `Alias.` offers public types only in a type position and public runtime values/routines only in an expression position; ordinary expression completion never offers record types. Field completion follows nested and imported record variables plus one- and two-dimensional indexed expressions. The project file format advertises both `.smileproj` and `.smilelibproj`.

Official libraries maintained with SMILE 2.0 are identified by the shared built-in-library catalog. Their imported aliases and qualified members use the teal **SMILE 2.0 Built-in Module or Library** editor classification, and Quick Info/completion labels them as a `SMILE 2.0 built-in library`. Student-created project and package libraries retain the ordinary identifier classification. The color can be customized in Visual Studio's Fonts and Colors settings without changing semantic ownership.

`Smile.Tests` constructs Base, Dependent, package-only consumer, mixed project/package consumer, ambient/transitive boundary, completion, package-manifest, fingerprint, diagnostic, and tolerant three-level recovery fixtures in temporary directories.

`libraries\Smile.Text.Extras` and `examples\Phase3ABasics` retain the typed-text reference coverage. `libraries\Smile.Data.Models` and `examples\Phase3BRecords` prove public record metadata and exact record identities through project and package references on Windows and Web. `examples\Phase3B1Hardening` proves collision-safe Web field keys and exact native/Web output; `examples\InvalidPhase3B1\ModuleCapture` proves a module cannot capture a consuming project's global record type. Imported completion presents public type/routine signatures while retaining private-type and direct-provider filtering; field completion follows variables, indexed array elements, nested fields, and public module record values.

`libraries\Smile.UI` is the Phase 5 reusable UI package. It owns no assets and exposes fixed-capacity, generation-safe Window, BitmapFont, Text, Menu, and Dialogue modules authored in ordinary SMILE. Pure menu-state routines remain callable from Console consumers, while drawing and transitive measurement routines carry `requiresGameWindow` through project and package references. Future RPG phases may compose this UI without adding inventory, battle, actor, tile-map, or camera rules to the generic library.

`libraries\Smile.Game` is the Phase 7 reusable 2D gameplay package. Its five ordinary modules provide cardinal movement/interpolation, animation timing, SMILE-MAP 1 parsing/rendering, camera math, and collision predicates without UI or assets.

`libraries\Smile.RPG` 1.2.0 contains fifteen ordinary modules: the Phase 6 data/management surface; World, Story, and Encounters; deterministic BattleEffects, BattleCore, BattleStrategy, and BattleView; visible-solid world invariants; and batch-aware format-2 transactional saves with format-1 compatibility. It has no Smile.UI or asset dependency. Battle presentation, quests, classes, and non-battle status policy remain application-owned or future work. See [the battle API](smile-rpg-battle-api.md).

Phase 8 retains `Smile.Game` 1.0.0 and `Smile.RPG` 1.1.1. The gap review found every dungeon-state requirement expressible through their existing public modules, so cardinal first-person projection, top-down floor rendering, door/key/chest/trap policy, dialogue text, and encounter-preview presentation remain application-owned in `examples\RpgDungeonGallery`. No dungeon-specific module, package dependency, or public API was added.

Phase 9 retains `Smile.Game` 1.0.0 and advances `Smile.RPG` to 1.2.0. The battle modules remain renderer-neutral and asset-free; `examples\RpgBattleGallery` owns the original DirectX, GDI, and Web presentation. SRPG writing remains format 2 with format-1 and format-2 reads because active battle sessions are intentionally not persisted.
