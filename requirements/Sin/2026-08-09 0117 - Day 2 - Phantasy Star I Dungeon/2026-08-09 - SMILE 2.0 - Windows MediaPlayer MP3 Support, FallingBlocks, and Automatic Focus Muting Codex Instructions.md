# 2. Non-negotiable technology decision

## Use Option 1 exactly

The MP3 music backend **must** use:

```text
Windows.Media.Playback.MediaPlayer
```

Use it from the native SMILE runtime through **C++/WinRT** and the Windows SDK.

This means:

```text
SMILE music statements
        ↓
MASM-generated native calls
        ↓
Small extern "C" runtime boundary
        ↓
C++/WinRT music module
        ↓
Windows.Media.Playback.MediaPlayer
        ↓
Windows Media Foundation and the built-in Windows MP3 decoder
```

## Do not substitute another playback technology

Do **not** replace the selected backend with any of the following:

- MCI or `mciSendString`;
- DirectShow;
- the legacy Windows Media Player SDK, COM control, or ActiveX control;
- `IMFMediaEngine`;
- a custom low-level Media Foundation playback pipeline;
- XAudio2;
- NAudio;
- FFmpeg;
- VLC;
- SDL, SFML, OpenAL, or another game/media framework;
- a codec pack;
- a Windows App SDK dependency;
- a third-party NuGet package;
- an external helper executable or PowerShell process.

`Windows.Media.Playback.MediaPlayer` is a Windows Runtime API. It is **not** the obsolete Windows Media Player desktop SDK.

Use the C++/WinRT projection headers already supplied by the installed Windows SDK. Link `WindowsApp.lib` explicitly. Do not add `Microsoft.Windows.CppWinRT` or another package unless Sin separately authorizes a package dependency.

# 3. Why this fits the newly committed graphics architecture

The current Direct2D/DirectWrite work correctly separates game-window services from graphics backends. GDI and DirectX are selected behind the common graphics router. MP3 playback must remain a separate native runtime service.

The music implementation must therefore:

- be independent of `graphics_gdi.c`;
- be independent of `graphics_directx.cpp`;
- work identically with `GraphicsBackend` set to `Auto`, `GDI`, or `DirectX`;
- survive resize and Alt+Enter transitions without restarting or stopping;
- require no rendering-backend conditionals;
- avoid changing frame pacing, VSync, drawing, scaling, or device-recovery logic;
- receive activation/minimization state only through the generic Win32 runtime, never through either graphics backend.

The only acceptable graphics-related edit is a project/build-file update required to compile the new native audio module. Do not place MediaPlayer code inside a graphics source file.

# 4. Preserve the existing WAV sound-effect system

SMILE currently implements:

```smile
PLAY SOUND "Assets\Move.wav"
STOP SOUND
```

through asynchronous Win32 `PlaySoundW` calls in `runtime.c`.

That implementation must continue to work. Do not redirect `PLAY SOUND` to `MediaPlayer` as part of this milestone.

The two channels must remain logically independent:

| Channel | SMILE surface | Windows implementation | Intended use |
|---|---|---|---|
| Sound effects | `PLAY SOUND` / `STOP SOUND` | Existing `PlaySoundW` path | Short WAV effects |
| Music | New music statements | `Windows.Media.Playback.MediaPlayer` | MP3 background music |

Required separation:

- `STOP SOUND` must not stop music.
- `STOP MUSIC` must not stop a WAV sound effect.
- Playing a WAV effect must not replace, pause, restart, or silence background music.
- Starting or stopping music must not alter the existing WAV behavior.

The one intentional cross-channel policy is **automatic whole-game focus muting**. When the SMILE game is not the active, non-minimized window, the native runtime must silence both channels. This is an automatic runtime policy, not the meaning of `STOP SOUND` or `STOP MUSIC`, and it must not alter the programmer's stored music-volume setting.

This separation is one of the main reasons for adding a distinct music subsystem rather than extending `PLAY SOUND` with MP3-specific behavior.

# 5. Approved beginner-facing SMILE syntax

Implement the following language surface:

```smile
PLAY MUSIC "Assets\Background.mp3"
PLAY MUSIC "Assets\Background.mp3" LOOP

PAUSE MUSIC
RESUME MUSIC
STOP MUSIC

MUSIC VOLUME 75
```

SMILE remains case-insensitive, so lowercase and mixed-case forms must parse identically.

## 5.1 Syntax meanings

### Play once

```smile
PLAY MUSIC "Assets\Background.mp3"
```

- Starts playback asynchronously.
- Returns immediately to the game loop.
- Does not freeze drawing, keyboard processing, or timing.
- Plays once unless `LOOP` is present.

### Play repeatedly

```smile
PLAY MUSIC "Assets\Background.mp3" LOOP
```

- Starts playback asynchronously.
- Sets `MediaPlayer.IsLoopingEnabled` to `TRUE`.
- Repeats automatically until `STOP MUSIC`, another `PLAY MUSIC`, or program shutdown.
- Do not implement manual loop polling or a frame-loop restart timer.

### Pause

```smile
PAUSE MUSIC
```

- Pauses at the current playback position.
- Safe when no track is loaded; it becomes a no-op.

### Resume

```smile
RESUME MUSIC
```

- Resumes a paused track from its saved position.
- Safe when no track is loaded; it becomes a no-op.

### Stop

```smile
STOP MUSIC
```

- Stops playback.
- Disconnects or resets the active source so that a later `PLAY MUSIC` starts at the beginning.
- Safe when no track is loaded; it becomes a no-op.
- Must not destroy the entire reusable music subsystem; final destruction belongs to runtime shutdown.

### Volume

```smile
MUSIC VOLUME 75
```

- Accepts a SMILE `NUMBER` expression.
- Uses a beginner-friendly range of `0` through `100`.
- Runtime behavior clamps values below `0` to `0` and values above `100` to `100`.
- Converts the value to MediaPlayer’s `0.0` through `1.0` range.
- Defaults to `100`.
- The selected volume remains in effect for the current track and later tracks during the same process.
- Setting volume before the first `PLAY MUSIC` must work.

Examples:

```smile
MusicLevel = 60
MUSIC VOLUME MusicLevel
```

```smile
MUSIC VOLUME MIN(100, Level * 10)
```

## 5.2 Required playback rules

1. SMILE exposes one background-music player per process.
2. Calling `PLAY MUSIC` while another track is playing replaces the previous source and starts the new request from its beginning.
3. Calling `PLAY MUSIC` again with the same path also restarts it from the beginning.
4. `LOOP` applies only to that `PLAY MUSIC` request.
5. A later non-looping request must disable looping left over from an earlier request.
6. A relative path is resolved from the generated executable’s directory, exactly as current game assets are resolved.
7. An absolute path may remain supported internally for development, but committed game source must use a relative path.
8. A missing, inaccessible, unsupported, or corrupt file must not crash the generated program.
9. MP3 is the required and tested music format for this milestone.
10. Do not make the grammar codec-specific. The statement is `PLAY MUSIC`, not `PLAY MP3`.
11. Do not promise other media formats in the public SMILE documentation during this milestone, even if MediaPlayer can decode them.
12. All music statements require a `GAME WINDOW`, consistent with the existing game-service model.
13. Every SMILE game must automatically silence **all game audio** while its game window is inactive or minimized, then restore normal audio policy when the game becomes the active, non-minimized window again.

## 5.3 Automatic whole-game focus mute

This behavior is owned by the native game runtime. A beginner must not need to write focus-handling code or add any SMILE statements to receive it.

Although Falling Blocks uses looping MP3 music, the policy applies to every `GAME WINDOW` program and to all game audio:

- looping or non-looping `PLAY MUSIC` playback;
- current and future `PLAY SOUND` WAV effects.

Treat game audio as audible only when **all** of these are true:

1. the SMILE application is active (`WM_ACTIVATEAPP` reports `TRUE`);
2. the SMILE top-level game window is active (`WM_ACTIVATE` is not `WA_INACTIVE`);
3. the game window is not minimized (`WM_SIZE` is not `SIZE_MINIMIZED`).

Maintain separate native state for application activation, top-level-window activation, minimization, and the resulting effective audio-active state. Do not let a later activation message incorrectly override a still-false condition from another state.

### When the game becomes inactive or minimized

The transition must be immediate and idempotent:

- Set the active `MediaPlayer.Volume` to `0.0`.
- Preserve the programmer/user-selected SMILE music volume separately as the **requested volume** from `0` through `100`.
- Do **not** pause, seek, stop, detach, or restart the music merely because focus was lost. Its playback timeline continues silently, including normal looping.
- Stop any WAV effect that is currently playing by calling `PlaySoundW(NULL, 0, 0)`.
- Suppress later `PLAY SOUND` requests while inactive so game logic continuing in the background cannot make noise.
- Do not modify the Windows master volume, another application, the user's Volume Mixer setting, or any system-wide audio state.

Stopping a short WAV effect is the correct inactive-window behavior because `PlaySoundW` does not provide a per-effect volume control. That old effect is not replayed when focus returns.

### When the game becomes active again

- Restore the active `MediaPlayer.Volume` from the stored requested SMILE volume, using `requestedVolume / 100.0`.
- Restore from the stored absolute value; never multiply or divide the current effective value, so repeated focus changes cannot cause volume drift.
- Do not call `MediaPlayer.Play()` merely because focus returned. Music that was manually paused must remain paused; stopped music must remain stopped; music that was already playing continues from its current timeline position.
- Re-enable future WAV `PLAY SOUND` requests. Do not replay an effect that was stopped or suppressed while inactive.

Additional required edge behavior:

- If `MUSIC VOLUME 0` was selected, focus return restores `0`, not an earlier nonzero value.
- If `MUSIC VOLUME` executes while inactive, remember the new requested value but keep the effective MediaPlayer volume at `0.0` until activation returns.
- If `PLAY MUSIC` executes while inactive, the source may load and its timeline may begin, but its effective volume remains `0.0` until the game is active again.
- `PAUSE MUSIC`, `RESUME MUSIC`, `STOP MUSIC`, and shutdown retain their normal meanings while inactive.
- Repeated or duplicate Windows activation messages must not restart music, replay effects, leak resources, or repeatedly change the requested volume.

# 6. Language-front-end changes

`src/Smile.Language` remains the sole source of truth. Do not create duplicate syntax rules in the compiler or Visual Studio extension.

Automatic focus muting adds **no new SMILE syntax**. Do not expose `FOCUS`, `ACTIVE WINDOW`, `MUTE ON FOCUS LOSS`, or similar statements in this milestone. The runtime must provide the behavior automatically for every `GAME WINDOW` program.

## 6.1 `Syntax.cs`

Add the minimum new keyword kinds needed for the approved syntax:

- `MusicKeyword`
- `PauseKeyword`
- `ResumeKeyword`
- `VolumeKeyword`

Reuse the existing `LoopKeyword` for the optional `LOOP` modifier.

Add case-insensitive keyword mappings:

```text
MUSIC
PAUSE
RESUME
VOLUME
```

Review and update any range-based keyword checks such as `SyntaxFacts.IsKeyword`. Do not accidentally leave the new words classified as identifiers.

Because the Visual Studio classifier consumes the shared language implementation, syntax highlighting should follow from the authoritative keyword table. Do not create a second keyword list in the extension.

## 6.2 `GameSyntax.cs`

Add a dedicated music syntax node. Do not overload `SoundStatementSyntax` with unrelated optional fields.

A suitable small model is:

```csharp
public enum MusicOperation
{
    Play,
    Pause,
    Resume,
    Stop,
    SetVolume
}
```

and a `MusicStatementSyntax` carrying only the data needed by each operation:

- operation;
- `MUSIC` token;
- optional path token;
- optional `LOOP` token or Boolean;
- optional volume expression;
- correct source span.

Use the smallest clear constructor/property design that matches the current syntax-tree style.

## 6.3 `Parser.cs`

The current parser routes every `PLAY` and `STOP` statement to the sound parser. Extend that dispatch without breaking current syntax.

Required forms:

```text
PLAY SOUND <string-literal>
STOP SOUND
PLAY MUSIC <string-literal> [LOOP]
PAUSE MUSIC
RESUME MUSIC
STOP MUSIC
MUSIC VOLUME <expression>
```

Recommended dispatch behavior:

- `PLAY SOUND` → existing sound parser;
- `PLAY MUSIC` → music play parser;
- `STOP SOUND` → existing sound parser;
- `STOP MUSIC` → music stop parser;
- `PAUSE MUSIC` → music pause parser;
- `RESUME MUSIC` → music resume parser;
- `MUSIC VOLUME` → music volume parser.

Do not silently accept these malformed examples:

```smile
PLAY MUSIC
PLAY MUSIC "Assets\Background.mp3" LOOP LOOP
PAUSE SOUND
RESUME SOUND
MUSIC 75
MUSIC VOLUME
STOP
```

Produce normal SMILE parser diagnostics and synchronize at the end of the current line.

## 6.4 `Semantics.cs`

For every music statement:

- require a `GAME WINDOW` somewhere in the program;
- allow use at top level or inside ordinary routines/control flow, just like `PLAY SOUND`;
- do not attempt static state-flow analysis such as requiring `PLAY MUSIC` before `PAUSE MUSIC`;
- make pause/resume/stop safe runtime no-ops when no source exists.

For `PLAY MUSIC`:

- require a non-empty text-literal path;
- retain the path as a literal, consistent with `PLAY SOUND`;
- do not require an absolute path;
- do not hard-code the developer machine’s drive or project root.

For `MUSIC VOLUME`:

- require a `NUMBER` expression;
- reject text and Boolean expressions;
- perform final range clamping at runtime so variable expressions remain safe.

Use a clear new music-specific diagnostic code, such as `SML3026`, if a new code is necessary. Do not change the meaning of existing `SML3024`, which currently belongs to sound playback.

# 7. MASM emitter changes

Update `src/Smile.Compiler/MasmEmitter.cs` using the existing native-call convention.

## 7.1 Required native exports

The generated assembly must be able to call:

```text
smile_music_play
smile_music_pause
smile_music_resume
smile_music_stop
smile_music_set_volume
smile_music_shutdown
```

## 7.2 Collecting syntax data

During the emitter’s collection pass:

- collect the path literal for `PLAY MUSIC` using the existing game-text-literal mechanism;
- collect the expression used by `MUSIC VOLUME`;
- detect whether the program uses any music statement;
- include nested routine and control-flow statements in that detection.

Add a small `_usesMusic` flag rather than forcing every generated program to reference the music implementation.

## 7.3 Emission behavior

Emit the operations as follows:

| SMILE statement | Native call |
|---|---|
| `PLAY MUSIC path` | `smile_music_play(path, length, 0)` |
| `PLAY MUSIC path LOOP` | `smile_music_play(path, length, 1)` |
| `PAUSE MUSIC` | `smile_music_pause()` |
| `RESUME MUSIC` | `smile_music_resume()` |
| `STOP MUSIC` | `smile_music_stop()` |
| `MUSIC VOLUME value` | `smile_music_set_volume(value)` |

Follow the existing Windows x64 calling convention and the emitter’s existing `EmitNativeCall` helper. Do not invent a second call convention.

## 7.4 Mandatory process cleanup

The native linker currently uses a custom MASM entry point:

```text
/entry:main
```

`END PROGRAM` currently calls `ExitProcess` directly. Therefore, do not assume that ordinary C++ global destruction or a CRT `atexit` path will clean up MediaPlayer.

When `_usesMusic` is true, emit an idempotent call to:

```text
smile_music_shutdown
```

in both places:

1. immediately before every generated `ExitProcess` path for `END PROGRAM`;
2. immediately before normal return from generated `main`.

This cleanup is required even when the SMILE source already contains `STOP MUSIC`, because stopping playback and destroying native resources are separate responsibilities.

Do not force the music object file into console programs or games that never use a music statement merely to call an empty cleanup function.

## 7.5 Do not emit focus polling

Do not inject focus checks into generated MASM, into the SMILE frame loop, or after every `SHOW SCREEN`. Win32 window activation is already owned by the native runtime window procedure. The emitter's responsibility remains only the explicit music statements and deterministic shutdown.

# 8. Native MediaPlayer module

Create a small dedicated module, for example:

```text
src/Smile.NativeRuntime/audio/music_mediaplayer.h
src/Smile.NativeRuntime/audio/music_mediaplayer.cpp
src/Smile.NativeRuntime/audio/audio_focus.h       (or an equivalently small internal header)
```

Keep the public boundary C-compatible so MASM can call it without C++ name mangling.

## 8.1 Required C ABI

Use this contract or an equivalent ABI with the same behavior:

```cpp
#ifdef __cplusplus
extern "C" {
#endif

void smile_music_play(const char* path, long long length, long long loop);
void smile_music_pause(void);
void smile_music_resume(void);
void smile_music_stop(void);
void smile_music_set_volume(long long volume_percent);
void smile_music_shutdown(void);

#ifdef __cplusplus
}
#endif
```

Do not expose C++/WinRT types to MASM, `runtime.c`, or the language/compiler assemblies.

## 8.2 Windows SDK headers

The implementation should use the Windows SDK C++/WinRT projection, including the minimum required headers, such as:

```cpp
#include <winrt/Windows.Foundation.h>
#include <winrt/Windows.Media.Core.h>
#include <winrt/Windows.Media.Playback.h>
#include <winrt/Windows.Storage.h>
```

Use:

```text
winrt::Windows::Media::Playback::MediaPlayer
winrt::Windows::Media::Core::MediaSource
winrt::Windows::Storage::StorageFile
```

Do not use XAML or `MediaPlayerElement`. SMILE provides its own native window and needs audio playback only.

## 8.3 Explicit initialization is mandatory

Generated SMILE executables bypass CRT startup by using `/entry:main`. Therefore:

- do not depend on a nontrivial global C++ constructor;
- do not depend on a global `MediaPlayer`, `MediaSource`, `std::string`, `std::mutex`, or smart pointer being constructed before `main`;
- initialize all nontrivial state explicitly and lazily on the first music operation;
- explicitly destroy it in `smile_music_shutdown`;
- make repeated shutdown calls harmless.

A plain zero-initialized pointer or POD state descriptor is acceptable. Allocate and construct the C++/WinRT state explicitly when first needed. Pair every successful initialization with explicit release.

Initialize Windows Runtime/COM once for the calling game thread, preferably with:

```cpp
winrt::init_apartment(winrt::apartment_type::multi_threaded);
```

Handle an already initialized apartment safely. Track whether this module owns the apartment initialization, and only uninitialize what this module successfully initialized.

## 8.4 Path handling

Music path behavior must match existing `PLAY SOUND` behavior:

- accept SMILE UTF-8 text plus its explicit length;
- convert it safely to UTF-16;
- detect absolute Windows paths;
- resolve relative paths against the generated executable’s directory, not the process’s current working directory;
- support spaces in paths;
- use bounded buffers or checked allocation;
- never concatenate past capacity.

Avoid maintaining two subtly different asset-path algorithms. The preferred small refactor is:

1. expose one internal C-compatible path resolver from `runtime.c` through a small internal header;
2. make both `smile_play_sound` and the new music module use it;
3. preserve all current WAV path behavior.

Do not turn this into a general virtual file system or asset manager.

## 8.5 Creating and playing the source

For a resolved absolute path:

1. obtain a `StorageFile` with `StorageFile::GetFileFromPathAsync(...).get()`;
2. create a `MediaSource` with `MediaSource::CreateFromStorageFile(...)`;
3. keep the active source alive for as long as the player uses it;
4. set `MediaPlayer.IsLoopingEnabled` from the SMILE `LOOP` flag;
5. set `MediaPlayer.Volume` from the remembered 0–100 music volume;
6. set `MediaPlayer.Source` to the new source;
7. call `MediaPlayer.Play()`.

Before assigning a new source:

- pause or detach the old source if present;
- clear and close the old source;
- ensure an earlier loop setting does not leak into the new request;
- start the requested file from its beginning.

Do not busy-wait for playback. Do not poll MediaPlayer from the game loop.

## 8.6 Pause, resume, stop, and volume

- `smile_music_pause` calls `MediaPlayer.Pause()` only when a player/source exists.
- `smile_music_resume` calls `MediaPlayer.Play()` only when a source exists.
- `smile_music_stop` pauses playback, disconnects the source, closes/releases the source, and leaves the reusable player ready for a later request.
- `smile_music_set_volume` clamps to 0–100 and stores it as the **requested** volume even before player creation.
- When game audio is active, apply `requestedVolume / 100.0` to `MediaPlayer.Volume`.
- When game audio is inactive, keep the effective `MediaPlayer.Volume` at `0.0` even if the requested volume changes.

Use MediaPlayer’s built-in `IsLoopingEnabled` property. Do not implement manual end-of-track callbacks merely to restart the same source.

## 8.7 Window activation and whole-game audio muting

`runtime.c` owns the Win32 window and the existing `PlaySoundW` channel, so it must own the authoritative effective-audio-active state.

Use separate zero-initializable flags similar to:

```text
smile_app_active
smile_window_active
smile_window_minimized
smile_game_audio_active
```

Derive:

```text
smile_game_audio_active =
    smile_app_active AND
    smile_window_active AND
    NOT smile_window_minimized
```

Update those inputs from the existing window procedure:

- `WM_ACTIVATEAPP`: `wParam != FALSE` controls application activation.
- `WM_ACTIVATE`: `LOWORD(wParam) != WA_INACTIVE` controls top-level-window activation.
- `WM_SIZE`: `wParam == SIZE_MINIMIZED` controls minimization while preserving the existing graphics resize behavior.
- Keep `WM_KILLFOCUS` clearing held-key state as it does now; do not use it as the only audio-activation signal.

Centralize transitions in one idempotent helper, for example:

```c
static void smile_update_game_audio_active(void);
```

On the transition to inactive, it must stop the current WAV with `PlaySoundW(NULL, 0, 0)`. `smile_play_sound` must return without starting a WAV whenever the effective state is inactive. `smile_stop_sound` remains safe and unconditional.

### Optional callback without unconditional WinRT linkage

Preserve the current static-library proportionality: `runtime.c` should not directly import a MediaPlayer symbol and thereby force the C++/WinRT object into every console program or WAV-only game.

Use a tiny optional internal callback boundary, for example in a neutral internal audio header:

```c
typedef void (*SmileMusicActivationCallback)(long long active);

void smile_audio_register_music_activation_callback(
    SmileMusicActivationCallback callback);
long long smile_audio_is_active(void);
```

Required behavior:

1. `runtime.c` implements the callback slot and the authoritative activation state.
2. The MediaPlayer module queries `smile_audio_is_active()` during lazy initialization.
3. The MediaPlayer module registers its internal activation callback after successful initialization.
4. The runtime calls the callback only when the effective active state actually changes.
5. The callback applies `0.0` while inactive or the stored requested volume while active.
6. The music module unregisters its callback before destroying its state in shutdown.
7. Programs with no music statement do not pull the C++/WinRT object merely because the generic window runtime exists.

An equally small design is acceptable if it preserves all of those linkage, lifetime, and behavior guarantees. Do not add a generalized event bus, service locator, plugin registry, or background thread.

All activation handling occurs on the existing game/window thread. Do not add locks or cross-thread dispatch unless the real API behavior proves it necessary.

## 8.8 Shutdown order

`smile_music_shutdown` must be idempotent and follow a safe order:

1. pause if appropriate;
2. disconnect the player from its source;
3. close/release the active `MediaSource`;
4. call `MediaPlayer.Close()` and release the player;
5. destroy explicitly constructed state;
6. uninitialize the Windows Runtime apartment only if this module owns that initialization;
7. clear all pointers/flags so a duplicate shutdown does nothing.

Do not leave a system media session or player object alive after the generated process exits.

## 8.9 Failure handling

Wrap C++/WinRT operations at the C ABI boundary so no C++ exception can cross into generated MASM code.

Catch at least:

- `winrt::hresult_error`;
- standard C++ exceptions if used;
- unexpected failures at the exported boundary.

On failure:

- leave the process running;
- stop/clear any partially installed source;
- return control to the game immediately;
- write a concise diagnostic with `OutputDebugStringW` or the project’s smallest existing native diagnostic mechanism;
- include the operation and HRESULT where available;
- do not show a blocking message box during normal gameplay;
- do not repeatedly spam the same failure every frame.

A missing or damaged MP3 is a nonfatal asset error, not a compiler or process crash.

The committed game must refer to it as:

```smile
"Assets\Background.mp3"
```

`FallingBlocks.smileproj` already includes:

```xml
<Asset Include="Assets\**\*" />
```

Therefore, do not add a redundant one-file asset entry unless the existing project-system behavior proves it is required. Validate that the wildcard copies the MP3 to the executable’s `Assets` directory.

## 10.2 Existing state meanings

Preserve the current state values:

```text
State = 0  → title screen
State = 1  → player alive / active game
State = 2  → game-over screen
```

Music is allowed only while `State = 1`.

## 10.3 Start music in `ResetGame`

Modify `SUB ResetGame()` so a new live game starts the background track in looping mode.

The relevant portion should have this behavior:

```smile
SUB ResetGame()
    ' Existing board, score, line, level, delay, and piece reset logic stays here.

    State = 1
    PLAY MUSIC "Assets\Background.mp3" LOOP
    CALL SpawnPiece()
END SUB
```

Exact placement may follow the existing routine structure, but these rules are mandatory:

- do not start music until the program is transitioning into a live game;
- title-screen drawing must not start music;
- a retry starts the track again from its beginning;
- `PLAY MUSIC` itself must replace/restart an earlier source safely;
- if `SpawnPiece()` immediately detects game over, `EndGame()` must stop the music.

## 10.4 Stop music in `EndGame`

Modify `SUB EndGame()` so music stops immediately when the player is no longer alive.

Required behavior:

```smile
SUB EndGame()
    State = 2
    STOP MUSIC

    ' Existing high-score save logic remains.
    PLAY SOUND "Assets\GameOver.wav"
END SUB
```

`STOP MUSIC` must occur before the game-over WAV is requested. The WAV must remain audible and independent.

## 10.5 Explicit exit cleanup in the game source

Update the Escape branch to demonstrate correct beginner-visible ownership:

```smile
IF Key = KEY_ESCAPE THEN
    STOP MUSIC
    STOP SOUND
    END PROGRAM
END IF
```

At the normal bottom cleanup, use:

```smile
STOP MUSIC
STOP SOUND
END PROGRAM
```

The runtime/emitter shutdown path is still mandatory as a safety net. The explicit SMILE statements make the game’s intent readable and test the language surface.

## 10.6 Prohibited Falling Blocks behavior

Do not:

- play music on the title screen;
- play music on the game-over screen;
- start music merely because the window opens;
- restart music once per frame;
- put `PLAY MUSIC` inside `DrawGame()`;
- poll the player from the SMILE game loop;
- stop music when a line clears or a piece moves;
- remove or replace current WAV effects;
- use `D:\SMILE 2.0\...` in committed SMILE code;
- add game-specific Falling Blocks behavior to the native runtime.

## 10.7 No game-source focus logic

Do not add focus polling, focus variables, volume-save variables, or focus-specific calls to `games\FallingBlocks\Program.smile`. The same automatic whole-game muting must work for every SMILE game through the generic Win32 runtime, whether the game uses GDI or DirectX.
